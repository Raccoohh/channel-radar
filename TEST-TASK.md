# Тестове завдання — Python/Backend розробник (внутрішні автоматизації)

**Формат:** самостійна робота, дедлайн — 3 дні.
**Результат:** git-репозиторій з робочим кодом і README **+ робоче публічне посилання** на
задеплоєний сервіс. Без другого — завдання вважається невиконаним, скільки б часу не
пішло на код.

## Контекст

Ми робимо внутрішні сервіси-автоматизації: збір даних із зовнішніх джерел без офіційних
API, обробка через LLM, віддача у вигляді дашборда. Реальний продукт — це не код у
репозиторії, а те, що працює для користувача за посиланням. Це тестове перевіряє саме
це: чи довів кандидат рішення до стану "я відкрив і воно просто працює", а не "має
працювати, якщо запустити правильно".

## Задача: `channel-radar` — живий дашборд аналітики Telegram-каналів

Сервіс, який збирає пости з публічних Telegram-каналів (анонімна web-прев'ю-версія
`t.me/s/<channel>`, без Bot API і без ключів — так само, як у попередніх версіях цього
завдання), зберігає їх, аналізує через LLM і показує в дашборді, куди я можу зайти
браузером у будь-який момент.

### Обов'язкова частина

1. **Збір**
   Фоновий процес (не обов'язково окремий воркер — крон-подібний тригер достатньо),
   який регулярно оновлює дані по вже доданих каналах. Інкремент — лише нове. Природний
   ключ, ідемпотентність — той самий стандарт, що й у попередніх версіях: повторний
   збір не створює дублікатів.

2. **Зберігання**
   БД у хмарі (безкоштовний tier — варіанти нижче), схема — на ваш розсуд, обґрунтуйте
   в README. Перегляди/реакції змінюються з часом — рішення "як зберігати динаміку, а
   не тільки останнє значення" лишається обов'язковим, як і раніше.

3. **Додавання каналу з інтерфейсу — ключова вимога**
   На сайті є поле "додати канал" (username без API-ключів). Я вводжу `@durov`, тисну
   кнопку — і за розумний час (секунди, не хвилини) бачу, що канал з'явився в списку і
   почав накопичувати дані. Це головна перевірка "продукт, а не CLI-скрипт для себе".
   Продумайте: що показувати, поки перший збір ще не завершився; що робити, якщо канал
   не існує або приватний.

4. **Дашборд**
   - Загальний огляд: список доданих каналів, ключові цифри по кожному (підписники,
     кількість постів, дата останнього збору, "здоров'я" джерела).
   - Сторінка каналу: графік/тренд метрик за час, список постів з переглядами/реакціями,
     фільтр за періодом.
   - Перегляд окремого поста — деталі, метрики, посилання на оригінал.

5. **AI-шар — обов'язковий, не бонус**
   Підключення до LLM з безкоштовним рівнем (див. розділ нижче) для змістовної обробки,
   не для галочки. Мінімум одне з:
   - дайджест/резюме каналу за період ("про що канал писав останній тиждень");
   - визначення теми/категорії поста;
   - позначення аномалій ("цей пост різко вище звичного для каналу").
   Явно опишіть у README: що робите, якщо LLM недоступний або впав у ліміт — дашборд не
   повинен через це лягти цілком.

6. **Деплой — обов'язкова частина, не інфраструктурна дрібниця**
   Сервіс має бути доступний за публічним URL у момент перевірки. Виберіть один
   безкоштовний варіант (нижче) і задокументуйте, чому саме він, з якими обмеженнями
   (холодний старт, засинання при неактивності, ліміт часу виконання, термін дії
   безкоштовної БД) і як ви ці обмеження врахували в рішенні.

7. **Тести**
   pytest, без мережі: нормалізація парсера на фікстурах, ідемпотентність збору,
   арифметика будь-якої аналітичної метрики. AI-виклики в тестах — замокані, не реальні
   (мережа й ключі в тестах заборонені так само, як завжди).

### На вибір (не обов'язково, оцінюємо як плюс, не як вимогу)

- Порівняння кількох каналів на одному графіку.
- Прості алерти ("канал не постив 3 дні").
- Експорт зрізу для LLM у форматі, сумісному з попереднім завданням `pulse`.

### Явно НЕ треба

- Kubernetes, мікросервіси, черги на кшталт Celery/RabbitMQ, платний хостинг.
- Автентифікація й ролі (сайт може бути публічним або за одним спільним посиланням).
- Ідеальний UI/дизайн-система — акуратний і зрозумілий вистачає.
- Обробка сотень каналів одночасно — досить, що працює для десятка.
- 100% покриття тестами.

## Де хостити безкоштовно (варіанти, обирайте один)

Немає єдино правильної відповіді — важливо, щоб обраний варіант реально був
безкоштовним і був обґрунтований у README з урахуванням його обмежень.

| Варіант | Що дає безкоштовно | Головне обмеження |
|---|---|---|
| **Render.com** | Web Service + фоновий cron job, Postgres на 90 днів | Сервіс "засинає" при неактивності — перший запит після сну довгий (десятки секунд) |
| **Fly.io** | Невелика VM завжди-безкоштовно | Потрібна власна конфігурація Postgres або зовнішня БД |
| **Railway.app** | Зручний деплой, невеликий стартовий кредит | Кредит не безкінечний — стежити, щоб не вимкнувся посеред перевірки |
| **Google Cloud Run** | Щедрий постійний безкоштовний ліміт запитів | Потрібна прив'язана картка на акаунті (сам сервіс безкоштовний у межах ліміту) |
| **Neon.tech / Supabase** | Безкоштовний Postgres окремо від хостингу застосунку | Комбінувати з хостингом застосунку з іншого рядка таблиці |
| **PythonAnywhere** | Просто підняти невеликий Flask/Django | Заплановані задачі на безкоштовному тарифі обмежені за частотою |

Практична порада, яку варто явно продумати: якщо хостинг застосунку "засинає" при
неактивності, як тоді відбувається регулярний фоновий збір? (Типове рішення — зовнішній
безкоштовний тригер, напр. GitHub Actions за розкладом або cron-job.org, що будить
сервіс HTTP-запитом.) Це саме той рівень рішення, який ми хочемо побачити
задокументованим, а не просто "у мене працює локально".

### AI-шар — де взяти безкоштовний ключ

- **Google AI Studio (Gemini, безкоштовний рівень)** — найпростіший шлях: безкоштовна
  квота на `gemini-2.0-flash` / `gemini-1.5-flash`, ключ видається без картки.
- Альтернативи: безкоштовні моделі через **OpenRouter**, безкоштовний рівень **Groq**.
  Обирайте будь-який — головне, щоб ключ не потрапив у git (`.env.example` без
  реального значення) і щоб обробка падіння/ліміту API була явно продумана.

## Документація (обов'язково)

- **README** — посилання на живий сервіс одразу у верхній частині; як запустити локально
  для перевірки коду; схема даних і чому саме така; що зроблено з AI-шаром і чому саме
  так; що не зроблено і чому; обмеження обраного безкоштовного хостингу.
- **`CLAUDE.md`** — межі шарів і домовленості проєкту для агента, не переказ README.
- **`docs/adr/`** — 1–3 короткі ADR на рішення, які дорого відкотити (вибір хостингу,
  схема зберігання динаміки метрик, вибір LLM-провайдера).

## Критерії оцінювання

| Критерій | Вага | На що дивимось |
|---|---|---|
| **Сервіс реально живий і відповідає** | 15% | Захожу за посиланням у момент перевірки — працює без танців з бубном |
| **Додавання каналу з інтерфейсу працює** | 25% | Ввожу новий канал у формі, за розумний час бачу дані по ньому |
| **Якість AI-шару** | 15% | Це змістовна обробка, а не сирий проксі-виклик без обробки помилок і без користі для читача |
| **Модель даних і розширюваність** | 20% | Природний ключ, ідемпотентність, зберігання динаміки метрик обґрунтовані |
| **Тести** | 10% | Покривають ризик (парсинг, ідемпотентність, арифметика), без мережі, AI замокано |
| **Комунікація рішень** | 15% | README/CLAUDE.md/ADR — чи зрозуміло, чому саме так, без дзвінка |

**Стоп-фактори:** посилання не працює в момент перевірки; секрети (ключі LLM,
креденшли БД) у репозиторії; тести ходять у мережу; кандидат не може пояснити власний
код на дзвінку.
